## Правила добавления кластеров для координатора

• Роль Client (Клиент). Для всех кластеров, от которых координатор принимает данные или которыми управляет (температура, влажность, реле, диммеры, энергомониторинг, кнопки), указывается роль EZB_ZCL_CLUSTER_CLIENT.
• Роль Server (Сервер). Сам координатор обязан иметь базовые серверные кластеры (Basic и Identify с ролью EZB_ZCL_CLUSTER_SERVER), чтобы корректно отвечать на запросы идентификации от других устройств в сети.


## Важные нюансы при работе с датчиками в этой схеме

1. Проприетарные кластеры Tuya и Xiaomi.
Многие устройства Tuya используют нестандартный кластер 0xEF00, а старые датчики Xiaomi/Aqara шлют данные в кластер 0x0000 (атрибут 0xFF01) или 0xFCC0. Для Tuya вы можете добавить в массив client_clusters значение 0xEF00, а для Xiaomi — 0xFCC0: функция ezb_zcl_create_cluster_desc() позволяет регистрировать любые произвольные 16-битные ID кластеров.
2. Обработка сырых команд и специфичных отчетов.
В zb_action_handler помимо EZB_ZCL_CORE_REPORT_ATTR_CB_ID (стандартные отчеты атрибутов) обязательно подпишитесь на колбэк EZB_ZCL_CORE_CMD_DEFAULT_RESP_CB_ID и сырые кластерные команды (например, для IAS Zone — EZB_ZCL_CORE_IAS_ZONE_STATUS_CHANGE_NOTIFICATION_CB_ID, так как датчики открытия и протечки шлют не отчет атрибута, а команду смены статуса зоны).
3. Автоматический биндинг при подключении.
Некоторые батарейные датчики (например, IKEA или Sonoff) после входа в сеть начинают слать отчеты только после того, как координатор отправит им ZDO-запрос на привязку (ezb_zdo_bind_req) к своему COORDINATOR_ENDPOINT (1) по нужному кластеру. Эту логику удобно запускать прямо из вашей программы на Go при получении события о новом устройстве (Device Announce).

## Назначение двух USB-портов на плате

На отладочных платах с ESP32-H2 (например, ESP32-H2-DevKitM-1) эти два разъема подключены к разным аппаратным интерфейсам чипа и имеют четкое разделение:
Разъем на плате	Куда подключен аппаратно	Как определяется в Linux	Назначение
### USB
	Напрямую к встроенному в ESP32-H2 контроллеру USB Serial/JTAG (пины GPIO26 и GPIO27).	/dev/ttyACM0	Встроенный аппаратный JTAG (для отладки GDB) + виртуальный COM-порт (CDC) для данных или прошивки.
### UART
	К внешнему мосту USB-UART на плате (например, CP2102 или CH343), который идет на пины UART0 (TX/RX).	/dev/ttyUSB0	Классический последовательный порт для вывода системных логов, загрузчика и прошивки.


## Как разнести логи и поток данных по двум портам

Для вашей задачи идеальная конфигурация — оставить системные логи ESP-IDF на порту UART (/dev/ttyUSB0), а высокоскоростной бинарный протокол координатора пустить через порт USB (/dev/ttyACM0). Тогда отладочные сообщения стека Zigbee никогда не попадут в ваш парсер на Go/C, а вы сможете в реальном времени смотреть логи в соседнем терминале.

### Настройка в idf.py menuconfig

Откройте конфигуратор проекта (idf.py menuconfig) и задайте следующие параметры:
1. Направляем системные логи в порт UART (/dev/ttyUSB0):
	• Перейдите в Component config -> ESP System Settings -> Channel for console output.
	• Выберите Default: UART0 (если стоял USB Serial/JTAG, поменяйте на UART0).
2. Отключаем вторичную консоль (чтобы логи не дублировались в USB):
	• В том же разделе найдите пункт Channel for console secondary output.
	• Выберите No secondary console.


### Важная особенность работы usb_serial_jtag при отключенном кабеле

У встроенного контроллера USB Serial/JTAG на ESP32-H2 есть нюанс: если кабель из разъема USB выдернут или программа на Linux закрыла порт /dev/ttyACM0, аппаратный буфер передачи (TX FIFO) перестает опустошаться.
• Чтобы задача Zigbee не зависла при вызове usb_serial_jtag_write_bytes(), всегда передавайте небольшой таймаут (например, pdMS_TO_TICKS(10) или pdMS_TO_TICKS(20)), а не portMAX_DELAY. Если хост не подключен, функция просто вернет 0 записанных байт через 10 мс, и координатор продолжит штатно работать.

### Как этим пользоваться на Linux

1. Подключите оба кабеля к ПК (или в продакшене оставляйте только USB).
2. Для просмотра системных логов и паник ESP-IDF запустите монитор на порту UART:
```
idf.py -p /dev/tty.usbmodem58970173491 monitor
```
3. Ваш координатор на Go или C открывает порт /dev/ttyACM0 (настройка скорости BaudRate для /dev/ttyACM0 формальна, так как USB CDC работает на полной скорости шины USB 2.0 Full-Speed — до 12 Мбит/с).

## Как связать ваш существующий код (под ZNP) с ESP32-H2

В протоколе TI ZNP ваш код на ПК работает через ограниченное число базовых примитивов. Чтобы перевести ваше ПО на ESP32-H2 с минимальными правками, достаточно сделать на ESP32-H2 эмуляцию именно этих 5–6 команд (в вашем бинарном формате по /dev/ttyACM0):

Команда в ZNP (CC2652)	Что делает ваше ПО	Аналог в прошивке ESP32-H2 (SDK v2.x)
ZDO_MGMT_PERMIT_JOIN_REQ
	Открывает сеть для добавления датчиков	ezb_bdb_open_network(duration)
ZDO_ACTIVE_EP_REQ + ZDO_ACTIVE_EP_RSP
	Запрашивает список эндпоинтов	ezb_zdo_active_ep_req() + отправка ответа в USB
ZDO_SIMPLE_DESC_REQ + ZDO_SIMPLE_DESC_RSP
	Запрашивает кластеры эндпоинта	ezb_zdo_simple_desc_req() + отправка ответа в USB
ZDO_BIND_REQ + ZDO_BIND_RSP
	Привязывает кластер датчика к координатору	ezb_zdo_bind_req() + отправка ответа в USB
AF_DATA_REQUEST
	Отправляет сырой ZCL-пакет устройству (включить реле, прочитать атрибут)	ezb_aps_data_req() или ezb_zcl_custom_cluster_cmd_req()
AF_INCOMING_MSG
	Получает любой входящий ZCL-пакет от датчика	Перехват через zb_action_handler / raw_cmd_handler и отправка в USB


## В сигнале Device(...) update: parent(...) status(X) tc_action(Y)
### Поле status (причина обновления статуса устройства в сети) 

• 0 (STANDARD_DEVICE_SECURED_REJOIN) — устройство выполнило защищённый повторный вход (Secure Rejoin) с актуальным сетевым ключом.
• 1 (STANDARD_DEVICE_UNSECURED_JOIN) — новое устройство впервые вошло в сеть (Unsecured Join) и запрашивает сетевой ключ (Transport Key).
• 2 (DEVICE_LEFT) — устройство покинуло сеть (отправило или получило Leave / Remove Device).
• 3 (STANDARD_DEVICE_TC_REJOIN) — устройство выполнило Trust Center Rejoin (переподключение с использованием известного Link Key, например ZigBeeAlliance09).


### Поле tc_action (действие центра доверия / Trust Center)

• 0 (AUTHORIZE / разрешить вход) — Trust Center разрешил устройству войти в сеть и отправил ему сетевой ключ (Transport Key).
• 1 (DENY / запретить вход) — Trust Center отклонил подключение (например, сеть закрыта Permit Join = 0 или не совпал Install Code).
• 2 (IGNORE / игнорировать) — Trust Center не предпринимает действий по выдаче ключа (например, когда устройство уже ушло status(2) или при дублирующих пакетах обновления).


## В сигнале Device(...) authorized: status(X) type(Y)

Этот сигнал срабатывает после завершения (или таймаута) процедуры согласования ключей Trust Center Link Key (TCLK).

### Поле type (тип процедуры авторизации)

• 0 (LEGACY / Pre-R21) — устройство вошло по старому стандарту (Zigbee HA 1.2 / до ревизии R21) без обмена индивидуальным TCLK (осталось на глобальном ключе ZigBeeAlliance09).
• 1 (R21 / Zigbee 3.0 TCLK Exchange) — устройство проходило процедуру обмена индивидуальным ключом центра доверия по стандарту Zigbee 3.0 (R21+).

### Поле status (результат авторизации)

• 0 (SUCCESS) — авторизация и обмен ключами прошли успешно.
• 1 (TIMEOUT / ошибка таймаута) — устройство не уложилось в отведённое окно времени для обмена TCLK (или не ответило на запрос проверки ключа Verify Key).
• 2 (FAIL) — ошибка криптографической проверки при обмене ключами.



## Зачем manuf_code (2 байта)
 У Aqara (Lumi = 0x115F), Tuya, Bosch и др. есть проприетарные атрибуты и команды. Передавая manuf_code в каждом пакете (0x0000 для стандартных кластеров ZCL), ваш ПК сможет управлять абсолютно любым устройством.

## Перехват всех входящих пакетов на ESP32-H2 (ESP-Zigbee-SDK)

В стандартных примерах Espressif приходится регистрировать каждый кластер отдельно, но для универсального моста нужно перехватывать все входящие ZCL-сообщения, которые не обработал сам стек.
В esp-zigbee-lib для этого используется обработчик необработанных команд (Raw ZCL handler) или регистрация callback-функции на уровне эндпоинта координатора:
```
// Регистрация перехватчика всех сырых ZCL-фреймов при инициализации координатора
esp_zb_raw_command_handler_register(zb_raw_zcl_handler);
```
## Архитектура очередей (Чтобы радио и UART не тормозили друг друга)

Если отправлять пакет в UART прямо внутри zb_raw_zcl_handler и ждать там ACK от ПК (150 мс), Zigbee-стек встанет на паузу и пропустит пакеты от других устройств. Поэтому на ESP32-H2 нужно сделать две очереди FreeRTOS:
1. uart_tx_queue (Очередь на ПК): zb_raw_zcl_handler мгновенно кладет пакет в эту очередь (за 5 микросекунд) и возвращается в радио-стек. Отдельная задача proto_tx_task берет пакеты из очереди по одному, присваивает SEQ, отправляет в UART и ждет ACK (с ретрансляцией при потере).
2. zb_cmd_queue (Очередь с ПК в радио): Когда proto_rx_task получает от ПК валидный пакет с новым SEQ, она сразу шлет ACK в UART, кладет команду в zb_cmd_queue и вызывает esp_zb_scheduler_alarm(), чтобы Zigbee-задача забрала команду и отправила её в эфир через esp_zb_zcl_custom_cluster_cmd_req().

## Три важные детали при сборке и запуске:

1. Поведение при рестарте Go-программы (is_first_rx_packet):
Обрати внимание на флаг is_first_rx_packet. Если ты перезапустишь программу на ПК, её счетчик tx_seq снова начнется с 1. Если в этот момент last_rx_seq на ESP32 тоже был равен 1, без этого флага первый пакет после перезапуска отбросился бы как дубликат. Рекомендую со стороны Go при старте первым делом отправлять CMD_SYS_PING (0xF0) с новым SEQ — он гарантированно обновит last_rx_seq на ESP32 и проверит связь.
2. Биндинг устройств (ZDO Bind Request):
Многие устройства (особенно датчики температуры/влажности, кнопки Aqara, умные розетки с энергомониторингом) не шлют отчеты координатору сами, пока ПК не выполнит им Bind на нужный кластер.

## вычисление контрольной суммы
uint16_t calc_crc16(const uint8_t *data, size_t len)
{
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < len; i++)
    {
        crc ^= data[i];
        for (int j = 0; j < 8; j++)
        {
            crc = (crc & 0x0001) ? ((crc >> 1) ^ 0xA001) : (crc >> 1);
        }
    }
    return crc;
}
